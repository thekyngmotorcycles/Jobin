# Jobeen · Inventario para la futura base nativa

Inventario de `package.json`, lockfile, árbol instalado, plugins de Expo y consumidores del repositorio. La base es Expo SDK 54, React Native 0.81.5 y New Architecture. El lockfile registra Expo 54.0.38. La presencia en el repositorio no acredita que un módulo esté incluido en la APK del Jelly 2. Este inventario no añade dependencias ni autoriza una compilación.

## Clasificación para una APK consolidada

El alcance funcional se toma de la hoja de ruta actualizada, incluidos descubrimiento y oportunidades. Los cambios de producto y monetización todavía no se implementan. [Hoja de ruta aprobada](https://github.com/thekyngmotorcycles/Jobin/blob/851573f50edbea46cab8ed1695ee7f22a0027225/docs/APPROVED_PRODUCT_ROADMAP.md)

| Clasificación | Base propuesta y criterio de inclusión |
| --- | --- |
| Imprescindibles para seguridad | Un almacenamiento seguro de secretos pequeños, con SecureStore como primera opción para evaluar en SDK 54. Si el producto debe conservar datos sensibles offline, seleccionar un único componente de cifrado autenticado por archivo o registro, con claves por cuenta protegidas por el sistema. Si se puede eliminar esa persistencia y recuperar del servidor, evitar agregar un módulo de cifrado sin uso. AsyncStorage y la copia de archivos disponible no aportan cifrado. |
| Imprescindibles para próximas funciones aprobadas | Reusar cámara, micrófono, picker y reproductor Expo para directos, Flashes y cursos. Seleccionar un solo SDK de emisión compatible con New Architecture para captura vertical inicial 9:16 y horizontal opcional 16:9, sin doble emisión inicial. Reusar Expo Notifications para avisos si el binario contiene el módulo. Cuando se apruebe habilitar compras, seleccionar una única integración nativa de facturación que cubra suscripciones premium, restauración y regalos digitales admitidos. |
| Opcionales y aplazables | Biometría local, BLE o SDK de gafas, controles externos de audio, bloqueo de orientación, DRM y descarga protegida, edición avanzada en el dispositivo, mejoras de audio, IA y grabación o emisión dual. Evaluar cada uno solo si hay un requisito concreto, equipo de prueba, soporte Android y mantenimiento compatible. |

- **Flashes y JHighlights.** Reutilizar captura, previsualización y selección. Probar recorte básico y publicación segura con procesamiento de servidor antes de incorporar codificador o editor nativo. Los clips de una grabación autorizada conservan permisos y derechos. Evaluar un editor nativo solo cuando sea imprescindible editar sin red o con requisitos de latencia no alcanzables en servidor.
- **Cursos y Creator Studio.** Reusar `expo-video` y subtítulos cuando el formato lo permita. Catálogo, módulos, progreso, métricas, moderación y derechos pertenecen al cliente JS y al servidor. El acceso a grabaciones premium exige autorización en el origen y CDN. Creator Studio puede aprovechar los módulos de directo, edición y reproducción sin un SDK separado para sus pantallas.
- **Premium y regalos.** El módulo de compras es una dependencia de la primera versión comercial que los habilite. Verificar renovación, cancelación, reembolso, restauración, idempotencia y derechos en servidor. Confirmar reglas de tienda, catálogo, costes y jurisdicción antes de elegir proveedor. La compra, el beneficio, la liquidación y el retiro son operaciones distintas.
- **Compatibilidad.** `package.json` y el lockfile vigentes ya resuelven cámara, notificaciones, reproducción, picker, FileSystem transitivo y Updates. Para cualquier biblioteca nueva, comprobar soporte explícito de Expo SDK 54, React Native 0.81 y New Architecture, y probar integración, permisos y Jelly 2. Una dependencia o permiso nativo cambia el alcance del runtime. Consolidar en una APK solo los módulos ya seleccionados y validados. Después, limitar OTA al runtime compatible y ensayar cambios de servidor y JS desde un canal de prueba.

## Videollamada privada para entrevistas individuales

Un mismo proveedor RTC puede cubrir captura y recepción en los dos flujos con un único SDK nativo. Para directos, usar salas con permisos de publicación y audiencia separados. Evaluar HLS y el reproductor Expo para audiencias grandes, con grabación voluntaria y egress autorizado. Para entrevistas, usar una sala privada con solo dos UUID autorizados por la convocatoria, invitación limitada, tokens cortos por sala y participante, expulsión y revocación al cancelar, y grabación, egress y transcripción desactivados por defecto. La agenda y el estado de la postulación pertenecen a Opportunities. El identificador de una sala jamás concede acceso por sí mismo. Conviene separar proyectos o credenciales para mantener aislados permisos, transmisión y métricas.

| Proveedor a validar | Alcance y costes públicos orientativos |
| --- | --- |
| **LiveKit**, primera opción para una prueba cuando se autorice compilación | El SDK React Native tiene integración Expo mediante plugins y permite salas RTC para ambos flujos. Se puede usar egress separado para HLS/RTMP del directo. Expo Go carece de los módulos nativos. LiveKit Cloud publica Build a US$0 y Ship desde US$50/mes, con consumo de WebRTC, transferencia y egress según plan. Probar expiración, expulsión y posibles reingresos con tokens emitidos justo antes de revocar. |
| **Agora**, alternativa | Un SDK React Native cubre llamada privada, directo interactivo y difusión por configuración de canal. La tarifa de lista publicada es US$3.99 por 1.000 minutos de vídeo HD RTC y US$1.99 por 1.000 minutos HD de audiencia broadcast, más funciones adicionales cuando apliquen. Por ejemplo, 100 entrevistas de 30 minutos con dos participantes suman 6.000 minutos RTC HD, unos US$23.94 a tarifa de lista antes de descuentos y extras. Confirmar compatibilidad Expo SDK 54 y New Architecture con la versión exacta antes de decidir. |

Medir ancho de banda, batería, estabilidad tras reconexión, audio externo, permisos, capacidad de excluir a C de una entrevista y separación de egress. Comparar regiones, tratamiento de datos, grabación, moderación y coste de audiencia. No incorporar dos SDKs por diferencias de interfaz. La selección queda pendiente de una prueba con hardware y presupuesto aprobados. ## Preparación del corte de credenciales (sin compilación)

- Lockfile verificado en esta rama: Expo 54.0.38, Supabase JS y Auth JS 2.118.0. No está presente expo-secure-store. No instalar otra versión de Expo ni actualizar el SDK de Auth incidentalmente. Confirmar las claves exactas usadas por la versión instalada para sesión, usuario y PKCE (incluidos posibles índices y slots de flujo) antes de conectar el adaptador; la allowlist actual solo admite la clave raíz y los sufijos -code-verifier y -user. Nunca ampliar a un prefijo arbitrario ni aceptar claves de otro proyecto.
- El candidato `credential-vault.ts` usa entradas de hasta 1200 bytes UTF-8, máximo 64 por valor. El manifiesto seguro pasa a pendiente antes de sustituir o eliminar fragmentos y vuelve a listo solo al completar la escritura; una interrupción no puede devolver un conjunto mezclado ni recurrir a AsyncStorage. Las pruebas usan un backend simulado y recrean la instancia del adaptador. La durabilidad física de cada operación del backend, el bloqueo entre procesos, pérdidas de claves o un fallo previo a persistir el marcador pendiente requieren prueba nativa; no garantizamos borrado físico ni revocación del servidor por esta lógica.
- Próxima integración: fijar versión de SecureStore compatible con SDK 54 mediante Expo, instalar y actualizar el lockfile en rama aislada, verificar permisos y plugin de backup; escoger accesibilidad no migrable entre dispositivos en iOS y evitar autenticación biométrica obligatoria para renovación de tokens en segundo plano. El adaptador se construirá una sola vez por instancia. Web necesita una solución separada (sesión de servidor/cookies HttpOnly según arquitectura); no exponer secretos al frontend ni sustituir el backend nativo por datos en claro.
- Preparar arranque sin sesión heredada, comprobar que el nuevo cliente no importa automáticamente tokens PKCE ni perfiles desde AsyncStorage. El corte requiere nuevo ingreso controlado (correo y Google), revocación de sesión anterior en servidor, identificación del propietario de claves de credenciales legadas y eliminación únicamente de claves exactas de Auth una vez autorizado. Nunca limpiar todo AsyncStorage, galerías ni borradores. Si el usuario no puede recuperar acceso o hay datos de titularidad ambigua, detener migración y conservar datos para recuperación restringida. Una APK antigua o un rollback no debe reactivar sesiones revocadas.
- Probar renovación real con GoTrue, tamaño máximo real de sesión, perfiles Unicode, OAuth/recovery y posibles claves adicionales del SDK, pérdida de red, dispositivo bloqueado, muerte de proceso durante escritura/eliminación, actualización sobre APK anterior, reinstalación y backup/restauración. Si el almacén falla, pantalla de acceso/recuperación segura; sin usar credenciales antiguas ni permitir pantallas privadas antes de confirmar identidad. Revisar rendimiento en Jelly 2; el adaptador fragmentado es candidato de evaluación, no decisión irrevocable.
- Datos privados grandes: preferir fuente de verdad del servidor y respaldos privados con control de titularidad. Los borradores offline, si deben persistir, requerirán almacenamiento autenticado y cifrado por cuenta, no almacenar fotos/videos enteros en SecureStore. Diseñar cifrado con librería auditada, no criptografía propia, pruebas de claves, recuperación y retención. No sincronizar automáticamente los datos legados sin consentimiento probado.
- Conservar una sola APK nueva consolidada cuando se hayan definido dependencias imprescindibles, requisitos de seguridad y capacidades de producto aprobadas. No iniciar workflows de Android, EAS build ni OTA sin autorización. Primero validar dependencias, plugins, exportación y fingerprint sin compilar; después solicitar aprobación con SHA fijo, runtime esperado, canal y backend de prueba separados, y plan de recuperación. Si el requisito de RTC/compras todavía no está definido, no incorporar SDK especulativos solo para evitar una recompilación futura. 

### Candidato de integración nativa
- Expo SDK 54: SecureStore 15.0.8, fijado en manifest y lock; Auth JS 2.118.0 mantenido. Contrastar integridad del paquete con npm antes de instalar en CI y ejecutar npm ci. Referencias: https://github.com/expo/expo/blob/sdk-54/packages/expo/bundledNativeModules.json y https://github.com/supabase/supabase-js/blob/v2.118.0/packages/core/auth-js/src/lib/helpers.ts .
- Confirmado el índice -flows-code-verifier y los slots -flow-{id}-code-verifier con identificador de 8–64 caracteres alfanuméricos, guion y guion bajo. Allowlist limitada a la raíz del proyecto. Soporte de slots no garantiza seguridad completa de callbacks antiguos o concurrentes; comprobar que el cliente preserve el flow_id y descarte callbacks de otra operación/sesión.
- Cliente candidato resuelve auth-storage.native.ts en Android/iOS, con SecureStore y vault fragmentado, servicio dedicado y accesibilidad no transferible a otro dispositivo (iOS). Plugin Android backup habilitado. El navegador conserva el mecanismo anterior; no constituye almacenamiento web cifrado. No se ha ejecutado la integración en Android, no se ha instalado una APK y no se ha activado en development. Las credenciales antiguas no se leen ni se importan; siguen pendientes la revocación/reautenticación y la limpieza comprobada del almacenamiento legado, recuperación ante fallos/instalaciones, OAuth/PKCE y validación física. No promover hasta completar esas condiciones.
